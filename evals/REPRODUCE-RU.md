# evals/REPRODUCE-RU.md — стенд для воспроизведения прогонов (русское зеркало)

Каноническая версия — английская: [REPRODUCE.md](REPRODUCE.md). Обе поддерживаются
параллельно; при расхождении побеждает английская.

Цель: на чистой машине, по этому файлу, без подсказок автора — довести smoke-прогон
до конца. Критерий готовности принят 2026-10-24: smoke дошёл → стенд собран верно;
полный прогон — потом и осознанно (~1 час GPU).

## 0. Честная оговорка о воспроизводимости (читать до сравнения чисел)

- **На референсном стенде (тот же GPU/драйвер/сборка llama.cpp), при
  per-question изоляции history и seed 42, extraction-выход побайтово
  идентичен внутри и между перезапусками сервера, включая аттракторные
  вопросы ([g1iso_determinism_check](results/g1iso_determinism_check.json),
  [g1iso_attractors_crosscheck](results/g1iso_attractors_crosscheck.json)).
  Ранняя невоспроизводимость была вызвана общими хвостами истории (разные
  промпты), а не GPU-недетерминизмом. Кросс-стендовый детерминизм (другой
  GPU/драйвер/сборка) не тестировался: внешние сравнения — полосами.**
- Поэтому **числа сравниваются полосами, а не до третьего знака**: чужой
  R@5 = 0.981 против нашего 0.987 — это тот же результат; 0.929 против 0.987 —
  это уже разница. Гварды пререгов задаёт сам проект; для внешнего сравнения
  держите полосу ±0.01–0.02.
- Полосы и классовые составы (mal/trunc/loop) переносимы между прогонами;
  по-вопросные пересечения — НЕ интерпретируются (канон ветки, Oct 2026).
- **Детерминизм (измерено 2026-10-25, пересмотрено в тот же день)**:
  побайтово-идентичные extraction-выходы держатся ВНУТРИ и МЕЖДУ перезапусками
  сервера — и для стабильных вопросов панели-12 (12/12,
  `results/g1iso_determinism_check.json`), и для аттракторных (9/9, включая
  8cf51dda/cc539528, через три инстанса сервера,
  `results/g1iso_attractors_crosscheck.json`). Межпрогонный дрейф классов
  (g1 vs g1-iso-a: capped ×3.5, loop ×3) объясняется РАЗЛИЧИЕМ ПРОМПТОВ —
  хвост истории перестраивал extraction на ~135/156 вопросов (хвостовые и
  изолированный прогоны совпадают лишь по ~20/156 векторов числа фактов; два
  хвостовых различаются на 31/156 из-за разного состава хвостов) — а не
  GPU-недетерминизмом. Классы сравниваются полосами; первая пуля этого раздела
  (GPU-разброс, эпоха prereg-v03) поставлена этим измерением под вопрос —
  на ревью владельца.
- **Конфаунд, обнаруженный 2026-10-25**: каждый прогон до H5-гарда (`ffb5879`)
  делил живой `~/.mem0/history.db` — хвост ≤10 сообщений предыдущего
  вопроса/прогона попадал в каждый extraction-промпт, извлечённые факты
  писались в живой history (форензика и мера влияния:
  `results/history_confound_forensics.md`; раскрытие:
  `results/history_confound_disclosure_note.md`).
- **Живой пример (сам стенд, записан с объяснением)**: старый smoke n=5 с
  токен-прокси (substr/покрытие токенов ответа в top-5) дал 5/5 (16 окт,
  билд до 9177, ctx 16384, без seed) и 0/5 (24 окт, билд 9177, ctx 32768,
  seed 42) — **артефакт хрупкой метрики-прокси n=5, а не регрессия стенда**:
  полный слайс single-156 в тот же день держал evidence-R@5 = 0.994 теми же
  серверами. Урок принят: smoke переведён на ту же evidence-R@5, что и полный
  прогон (ожидаемое значение на рабочем стенде — 5/5); старый прокси остался
  вторичной диагностической строкой и НЕ является метрикой.

## 1. Аппаратное

- GPU ≥ 12 GB VRAM (наш стенд: RTX 5060 Ti 16 GB, backend Vulkan);
  живой расход: ~8.8 GB LLM-сервер + ~0.2 GB эмбеддер.
- Время: smoke n=5 ~5–10 мин; полный single-156 ~53–66 мин (~24–40 с/вопрос).

## 2. Python-окружение

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt   # точные версии; mem0 — git-пин коммита
```

`requirements.txt` зафиксирован по венду стенда (34 пакета). mem0 установлен
не из PyPI, а **точным коммитом upstream** `mem0ai/mem0@0724291b…` (чистый
detached-чекаут, без локальных правок) — между релизами 2.2.x; это не опечатка.

## 3. LLM-сервер

1. Соберите llama.cpp (наш билд: **9177, коммит 366c5e2a**, backend Vulkan).
2. Скачайте модель: `bartowski/Meta-Llama-3.1-8B-Instruct-GGUF`,
   файл `Meta-Llama-3.1-8B-Instruct-Q4_K_M.gguf`
   (`https://huggingface.co/bartowski/Meta-Llama-3.1-8B-Instruct-GGUF`),
   размер 4 920 739 232 байта, **md5 `6eb593f3f5eee264d6c60c186ccc12e0`** — сверьте.
3. Запуск (наш стенд; `--device` у вас может быть другим — проверьте
   `llama-server --list-devices` и возьмите свой dGPU):

```bash
llama-server -m Meta-Llama-3.1-8B-Instruct-Q4_K_M.gguf -c 32768 -ngl 99 \
  --device Vulkan1 --host 127.0.0.1 --port 8085 --seed 42
```

- `ctx 32768` и `--seed 42` — часть методологии, не менять.
- Сервер запускается БЕЗ `--api-key` → любой bearer подходит (скрипты
  подставляют `local` сами, см. §5).
- Дефолт `repeat_penalty` этого билда = 1.0 (выключен) — прогоны идут на нём;
  лечение loop-класса пенальти — отдельная тема ветки, в воспроизведение
  базовых прогонов не входит.

## 4. Эмбеддер

Любой OpenAI-совместимый embeddings-сервер с `nomic-embed-text-v1.5`
(768 измерений). Наш стенд: LM Studio (`lms load text-embedding-nomic-embed-text-v1.5`,
порт 1449). Подойдёт и llama-server с GGUF-версией nomic — важно только
совпадение модели и размерности с переменными §5.

## 5. Переменные окружения (все с дефолтами стенда — можно не задавать)

| Переменная | Дефолт | Когда переопределять |
|---|---|---|
| `LLM_BASE_URL` | `http://127.0.0.1:8085/v1` | другой порт / Ollama / LM Studio |
| `EMBED_BASE_URL` | `http://127.0.0.1:1449/v1` | другой эмбеддер-сервер |
| `LLM_MODEL` | `Meta-Llama-3.1-8B-Instruct-Q4_K_M.gguf` | другое имя модели в API сервера |
| `EMBED_MODEL` | `text-embedding-nomic-embed-text-v1.5` | другой эмбеддер |
| `EMBED_DIMS` | `768` | другая размерность |
| `LLM_API_KEY` | содержимое `LLM_API_KEY_FILE`, иначе `local` | сервер с авторизацией |
| `LLM_API_KEY_FILE` | `/tmp/opencode/pilot8085.key` | конвенция вашего стенда |
| `EMBED_API_KEY` | `local-smoke` | эмбеддер с авторизацией |
| `EVAL_GUARD_PATHS` | (пусто) | доп. охраняемые корни, через двоеточие (гард изоляции, §6) |

Файл ключа **создавать не нужно**: если его нет (и не задан `LLM_API_KEY`),
скрипты подставляют `local` — сервер без `--api-key` принимает любой bearer.

Один источник: `evals/eval_config.py` — все раннеры импортируют оттуда;
литеральных адресов в коде прогонов больше нет.

## 6. Гард изоляции (MAQS H5 [CRIT]) — встроен в каждый раннер

Каждый раннер (`run_single156_*`, зонды, smoke-пилоты) оборачивает свой
`main()` декоратором `@guarded()` из `evals/isolation_guard.py`: живые корни
снимаются в момент импорта (гард импортируется ДО `from mem0 import Memory` —
побочные эффекты импорта попадают в охраняемое окно), после тела прогона те
же корни перечитываются и сравниваются. Любое расхождение печатает строки
`[H5 isolation guard] RED` и делает exit-код 1 — проверка выполняется, даже
если тело прогона упало с исключением. Это расширение линии H5 из MAQS
[Unreleased]: гард изоляции исполняется в КАЖДОМ прогоне, встроен в раннер,
а не периодически.

- **Охраняемые корни** (живые хранилища = всё вне temp-стора прогона):
  `~/.mem0` (дефолтный каталог mem0: `history.db`, `config.json`,
  `migrations_qdrant/` и всё внутри), `~/.local/share/qdrant`,
  `~/.cache/qdrant` плюс доп. корни из `EVAL_GUARD_PATHS` (через двоеточие).
  Несуществующие корни охраняются как пустые: всё, что в них появилось за
  прогон, — утечка, гард краснеет.
- **Семантика сравнения**: SQLite-файлы (`*.db` и т.п.) сравниваются по
  ЛОГИЧЕСКИМ СТРОКАМ, не по md5 — чекпоинт WAL переписывает байты основного
  файла без изменения данных, побайтовое сравнение живой WAL-базы дало бы
  ложное RED (известная ловушка чекпоинта). Побочные файлы
  `-wal`/`-shm`/`-journal` игнорируются как транзиентные. Всё остальное
  сравнивается sha256 байтов. Появление/исчезновение файлов в охраняемом
  корне — тоже расхождение.
- **Редирект history (PER QUESTION)**: раннеры передают
  `"history_db_path": temp_history_db(f"{STORE}/q{qi}")` в конфиге mem0 —
  одна history-база НА ВОПРОС, `get_last_messages` пуст для каждого
  extraction-вызова. Без него mem0 v2.2.1 держит history-базу в
  `~/.mem0/history.db` и не только ЗАПИСЫВАЕТ туда каждую инжестируемую сессию,
  но и подмешивает последние 10 сообщений того же scope в каждый
  extraction-промпт (секция «## Last k Messages»). Все прогоны до 2026-10-25
  шли с этим живым заражением (форензика:
  `results/history_confound_forensics.md`). Первый вариант редиректа (per-RUN,
  одна temp-history на все вопросы прогона) сохранял внутрипрогонный
  скользящий хвост — вскрыт СТОПом g1-iso-a 2026-10-25
  (`results/g1iso_a_note.md`) и заменён в тот же день; сам гард от гранулярности
  не зависит.
- **Самотест** (без стенда):
  `python3 evals/isolation_guard.py selftest` — пишет пробный файл в
  `~/.mem0`, ждёт RED, удаляет, ждёт GREEN; exit 0 только если оба сошлись.
- Честная оговорка: НЕ-прогонный процесс, легитимно пишущий в живой стор во
  время прогона, тоже краснит гард; отчёт о расхождении называет пути —
  решение за человеком.

## 7. Порядок проверки стенда

```bash
# 1) статический гейт — стенда не требует вовсе:
python3 schemas/maqs_way_audit.py all          # ждём: GATE GREEN

# 2) smoke (5 стратифицированных вопросов, ~5–10 мин):
python3 evals/pilot_longmemeval_n5.py
# ожидаем: 5 строк [n/5] + 'SMOKE VERDICT: evidence-R@5 (n=5) = 1.00 (stand OK)'
# + '[H5 isolation guard] GREEN — live stores untouched.' (§6);
# evidence 5/5 на рабочем стенде — осмысленный знак; token-proxy рядом —
# вторичная диагностика, НЕ метрика (может быть 0/5, см. sec 0); артефакт
# пишется таймстампным именем и ничего не затирает

# 3) полный прогон (референсная конфигурация g1 — грамм-бейзлайн):
python3 evals/run_single156_g1.py               # ~1 час, чекпоинт на каждый вопрос
```

Результаты пишутся в `evals/results/` (JSON с провенансом: модель, сервер,
seed, дата). Исторические раннеры (`*_oldcfg/fixcfg/b6/b4/ii`) соответствуют
пакетам пререгов `evals/prereg-*.md` — гонять их стоит только с пререгом.

## 8. Что НЕ входит в этот рецепт

- Постхок-анализ вербатим-метрики (`verbatim_*.py`) читает живые Qdrant-сторы
  из `/tmp` — они эфемерны; после полного прогона стора живёт до перезагрузки.
- Прогоны ветки B6 требуют тех же пререгов и санкций, что и у автора —
  воспроизводятся числа, а не процесс принятия решений.

## 9. Отчёт о попытке воспроизведения

Независимое воспроизведение — настоящий тест этого рецепта, поэтому отчёт полезен
в любом исходе — удачном или нет.

1. **Собирайте стенд только по этому файлу.** Пожалуйста, не спрашивайте автора
   о помощи по ходу: каждая точка, где пришлось спросить, — дыра в рецепте.
2. **Записывайте каждую точку, где пришлось догадываться**, искать что-то в
   других местах или отклоняться от инструкций (другая ОС, GPU, сервер, сборка
   модели, порт). Эти записи — самая ценная часть отчёта.
3. **Приложите**:
   - строку `SMOKE VERDICT` из `python3 evals/pilot_longmemeval_n5.py`;
   - вывод `python3 schemas/maqs_way_audit.py all`;
   - `pip freeze` окружения, в котором шёл прогон;
   - ОС, GPU и VRAM, сборку llama.cpp, md5 файла модели.
4. **Откройте issue** с заголовком `Reproduction report: <ваша конфигурация>`.
   Неудачные и частичные попытки приветствуются: они записываются так же, как
   успешные, и никогда не переписываются молча.

Smoke-результат `evidence-R@5 = 1.00` означает, что стенд работает. Меньшее
значение — не обязательно провал. Присылайте как есть, вместе с журналом
отклонений.
