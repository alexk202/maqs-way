# H5 isolation guard — отчёт о пакете (гард + smoke GREEN + негативный RED, 2026-10-25)

Задача (расширение H5 из MAQS [Unreleased]): гард изоляции исполняется в КАЖДОМ
прогоне, встроен в раннер, не периодически. Проверка обещания `evals/README.md`
(«guard check before/after live directories») показала: **обещание не исполнялось**
— в раннерах не было ни снимка, ни сравнения. Хуже — при аудите найдена живая
утечка, которую гард и должен ловить.

## Найденная утечка (mem0 v2.2.1 @0724291, все раннеры до 2026-10-25)

Ни один раннер не задавал `history_db_path` → mem0 использовал дефолт
`~/.mem0/history.db` (живой стор). Механизм двунаправленный:

- **ЗАПИСЬ**: `Memory.add(infer=True)` сохраняет каждую инжестируемую сессию в
  живую базу (`SQLiteManager.save_messages`, main.py:1207); с 16–17 октября
  там накопилось 7 462 912 байт / 22 940 строк сырого контента хейстаков.
- **ЧТЕНИЕ В ПРОМПТ**: тот же `add()` читает `get_last_messages(scope, limit=10)`
  (main.py:922) и подмешивает их в extraction-промпт секцией «## Last k Messages»
  (prompts.py:1037). Все раннеры используют `user_id="u_pilot"` → в каждый
  extraction-вызов попадал неконтролируемый хвост ПРЕДЫДУЩИХ вопросов того же
  прогона и ПРЕДЫДУЩИХ прогонов (b1/b2/n50/stratified-50/ii…), т.е. утечка
  загрязняла и живой стор, и экспериментальный канал.

Раскрытие для замороженных пакетов (g1/ii/b4/b6/fixcfg/oldcfg/зонды): измеренные
числа получены С этим заражением extraction-канала; сравнения внутри линии
(apples-to-apples между прогонами с одним и тем же механизмом) не обесценены,
но любой ре-ран после редиректа даст чуть иной extraction-контекст (без
межпрогонного хвоста). Решение о переоценке — за советом; гард гарантирует,
что дальнейшие прогоны живые каталоги не трогают.

## Что построено

- **`evals/isolation_guard.py`** (рядом с `eval_config.py`): снимок живых корней
  при импорте модуля (импорт гарда в раннерах стоит ДО `from mem0 import
  Memory` — побочные эффекты импорта внутри охраняемого окна) → прогон →
  `verify()`; расхождение → строки `[H5 isolation guard] RED` + **exit 1**
  (проверка выполняется и при падении тела прогона).
  Охраняемые корни: `~/.mem0` (history.db, config.json, migrations_qdrant/ и всё
  внутри), `~/.local/share/qdrant`, `~/.cache/qdrant` + `EVAL_GUARD_PATHS`
  (через двоеточие). Несуществующие корни охраняются как пустые.
  Сравнение: SQLite — по ЛОГИЧЕСКИМ СТРОКАМ (все таблицы, `mode=ro&immutable=1`),
  **не по md5** — чекпоинт WAL переписывает байты без изменения данных (известная
  ловушка); `-wal/-shm/-journal` игнорируются как транзиентные; прочие файлы —
  sha256 байтов; появление/исчезновение файлов — тоже расхождение.
- **Встройка**: все 13 раннеров (`run_single156_{b4,b6,g1,ii,fixcfg,oldcfg}`,
  `run_b3_empty_probe`, `run_g1_probes`, `run_reppenalty_probe`,
  `pilot_longmemeval_n5`, `pilot_mem0_smoke`, `pilot_lme_evidence`,
  `verify_fix1`) обёрнуты `@guarded()`; постхок-инструменты (verbatim_*,
  diag_rank*, check_conditions) mem0 не инстанцируют и гард не получили.
- **Редирект history**: в конфиг mem0 каждого раннера добавлен
  `"history_db_path": temp_history_db(STORE)` — history-канал уведён в
  temp-стор прогона (`pilot_mem0_smoke` — `/tmp/opencode/mem0qdrant_smoke`).
  Это ЕДИНСТВЕННАЯ конфиг-дельта раннеров; retrieval-путь (LLM/embedder/qdrant/
  параметры) не тронут. Документация: README (Isolation), REPRODUCE.md §6
  (EN, канон) + REPRODUCE-RU.md §6 (зеркало), таблица §5 `EVAL_GUARD_PATHS`.

## Честные оговорки

- Гард ловит ЛЮБУЮ запись в живые корни, включая легитимную стороннюю
  (не-прогонную) активность во время прогона: отчёт называет пути, решение за
  человеком.
- При SIGKILL раннера проверка не выполняется (нет нормального выхода) — это
  ограничение дизайна «снимок при импорте → verify на выходе main», задокументировано.
- `history.db` в temp-сторе одноразовый (per-run) — межпрогонной истории
  extraction больше не видит; внутрипрогонную последовательность вопросов
  (как было) сохраняет.
