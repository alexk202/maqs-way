# Форензика общего mem0 history.db — что он делал с замороженными числами (2026-10-25)

Пакет по ТЗ «проверка влияния общего mem0 history.db на замороженные числа» (после
H5-гарда, `ffb5879`). Без GPU, только чтение: `~/.mem0/history.db` открывался
исключительно `mode=ro&immutable=1`, сторы читались с копий в
`/tmp/opencode/forensics_work`, ничего в живых каталогах не менялось
(подтверждается гардом в этой сессии). Механические данные —
`history_confound_forensics.json` (рядом), инструмент —
`evals/history_confound_forensics.py`.

## 0. Поправка к формулировке `ffb5879` (append-only)

Коммит `ffb5879` описал живой `~/.mem0/history.db` как «7 462 912 байт / 22 940
строк сырого контента хейстаков». Точно по размеру и числу строк, неточно по
содержанию: 22 940 строк — это таблица `history` (события ADD **извлечённых
фактов**, main.py Phase 6 `batch_add_history`), а сырые сообщения живут в таблице
`messages`, где `save_messages` (storage.py) после каждой вставки **вытесняет всё,
кроме 10 новейших строк по scope** (`DELETE … ORDER BY created_at DESC LIMIT 10`).
Полного журнала сессий в живом db никогда не было — только скользящий хвост-10.
Двунаправленный механизм подтверждён: чтение `get_last_messages` (main.py:922) в
секцию «## Last k Messages» extraction-промпта (prompts.py:1037) работало в каждом
`add(infer=True)` всех замороженных прогонов; запись фактов в живой history — тоже.

## 1a. Что get_last_messages подмешивал в extraction-промпт каждого вопроса

Реконструкция: полный реплей **2 185 add-вызовов** всех 18 пре-редиректных прогонов
(порядок вопросов и чанкинг воспроизведены по раннерам/артефактам) против
in-memory SQLite с SQL из storage.py дословно. **Валидация реплея**: финальные
остатки-10 обоих eval-scope (`u_pilot`, `u_probe`) совпали с живым db
посимвольно → реконструкция хвостов достоверна.

Классы хвоста для каждого вызова: `EMPTY` (таблица пуста), `SAME_Q` (хвост из
предыдущего чанка того же вопроса), `CROSS_Q` (хвост — сессия предыдущего вопроса
того же прогона), `CROSS_RUN` (хвост — последняя сессия предыдущего прогона).
`CROSS_Q + CROSS_RUN` = заражённые вызовы.

Ключевое: **каждый extraction-вызов single-156 линию получал до 10 чужих
сообщений** (хвост предыдущего вопроса; для первого вопроса прогона — хвост
последней сессии предыдущего прогона). Примеры (реплей, валидирован):

- g1, вопрос 0 (8a2466db): хвост = 10 сообщений о карамели/выпечке — последняя
  сессия **b4** (f4f1d8a4_abs) — межпрогонное заражение b4→g1.
- g1, вопрос 1 (06878be2): хвост = 10 сообщений о Premiere Pro из сессии вопроса
  8a2466db — внутрипрогонное.

Какие именно 10 из >10-сообщенийной сессии — выбор SQLite при тай-брейке равных
`created_at` (в одной вставке все строки получают один timestamp); для >10-сообщенийных
сессий точный состав хвоста невосстановим (вытеснен), источник хвоста — восстановлен
точно. Отдельная неопределённость: тест 18:18:29 20.10 перед b6 (12 фактов одним
батчем) — scope неопределим post factum (u_pilot|u_calib|u_probe); влияет только на
атрибуцию хвоста первого вопроса b6 (в обеих ветках — чужой), не на доли.

## 1b. Доходило ли заражение до сторов (прямая мера)

Метод: индекс 5-словных шинглов, **уникальных ровно для одного вопроса** из 500
(1 346 871 шингл); факт вопроса q, несущий ≥2 уникальных шингла ДРУГОГО вопроса =
подтверждённая утечка (≥3 — «сильная»; один — слабая). Пороги консервативны:
уникальный шингл не может лежать в собственном хейстаке q по построению.

Каналы: **store** (живые сторы /tmp: b4, g1, ii, b3-probe, g1-probes — читаны с
копий; атрибуция по порядку вопросов прогона — точная), **history_adds** (события
ADD живого history; атрибуция кластеров по DP-выравниванию контента; для прогонов
с утерянными сторами — единственный канал), **artifact_top5** (top-5 из
коммитных артефактов n5/n50/strat/full-500 — точная атрибуция).

Кросс-валидация атрибуции: g1 — 118/156 вопросов имеют полное пересечение
store∩history, 1255/1680 фактов совпадают под тем же вопросом; DP-дрейф ~25%

порядка, store-каналы b4/g1/ii — надёжные 16–18%).

Разбивка store-утечек по источнику (механизм подтверждён):
- g1: 274 = **223 от прямого предшественника** + 22 от пред-предшественника
  (смешанный хвост <10-сообщенийных сессий) + 29 cross-run/прочее; 84% фактов
  с ≥3 уникальными шинглами.
- b4: 376 = 304 + 39 + 33; ii: 327 = 267 + 37 + 23.

Ручная верификация (5 фактов, g1/06f04340): в сторе вопроса лежат факты «virtual
coffee breaks», которых **нет в его собственном хейстаке** и которые дословно есть
в хейстаке предшественника (54026fce) — хвост → extraction → стор, конец-в-конец.

**Вывод 1b ≠ 0: заражение дошло до сторов.** Порядок: ~16–18% хранимых фактов
single-156 линии несут дословный чужой контент (в ~57% вопросов). При этом
в **retrieval** чужие факты почти не всплывали: top-5 артефактов full-500 — 1.8%
фактов, 38/500 вопросов — согласовательно с тем, что evidence-R@5 линию (0.98–1.00)
конфаунд не обрушил; однако классы состава (total memories, loop, capped,
verbatim-метрика) могли питаться хвостовыми артефактами — их сдвиг и проверяет
g1-iso.

## Границы вывода (честно)

- Frozen числа НЕ переписываются; всё сравнение внутри линий (b2↔g1↔ii) шло при
  одном и том же механизме (хвост в каждом вызове) — apples-to-apples по каналу;
  но полосы классов и composition-флаги теперь несут известный посторонний
  вклад, величина которого измерена выше.
- Ранние прогоны без пина seed не объясняются этим конфаундом (это отдельная
  GPU-тема); что хвост добавил, а что GPU — разделит только g1-iso с пином.
- Невосстановимо: точный по-строчный состав хвостов для сессий >10 сообщений
  (тай-брейк + вытеснение) — восстановлены источники и доли, не буквальные
  хвосты; scope пред-b6 теста; paraphrase-утечки ниже порога шинглов (учтены
  только дословные ≥2 шинглов — консервативная нижняя граница).
- Сегодняшние (25.10) прогоны — изолированные: живой history.db не менялся
  (mtime 24.10 18:47), все записи в temp — гард и редирект работают.
