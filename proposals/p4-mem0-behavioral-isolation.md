# P4: поведенческий тест кросс-пользовательской изоляции mem0 (v0.1, NOT canon — дизайн на ревью, НЕ запускать)

> Status: design proposal for owner review, 2026-10-26. NOT canon, NOT run.
> Реализация — один скрипт + stub-эмбеддер, CPU, секунды; вердикт — только
> после санкционированного запуска. Рамка (решение Совета 26.10): утечка
> 25.10 — дефект НАШЕГО стенда (один user_id, общая history), НЕ mem0; P4
> проверяет чужой класс — изоляцию МЕЖДУ пользователями.

## 1. Цель

Доказать поведенчески (исполняемым тестом на чужой системе), что mem0@0724291b
изолирует пользователей по всем каналам чтения:

- **search** (векторный путь: retrieval по фильтру user_id);
- **get_all** (перечисление по user_id);
- **канал истории / last-messages** (SQLiteManager: таблицы messages/history
  ключуются session_scope = `user_id=<id>`; чужой scope не должен видеть ни
  строк, ни — при extraction — хвоста чужих сообщений в
  `get_last_messages` → «## Last k Messages»).

Ожидание по всем каналам: **чужого 0 в обе стороны** (A↔B, A↔C, B↔C).

## 2. Стенд-инвариант: без LLM, детерминированно, CPU

- mem0 — точный апстрим-пин из канон-`requirements.txt`
  (`mem0ai/mem0@0724291b`), свежий venv.
- **infer=False** (raw per-message adds) — extraction-LLM не вызывается вовсе;
  тестируется изоляция ХРАНИЛИЩ, не генерация.
- **Эмбеддер-заглушка**: мини-HTTP-сервер (один файл, ~30 строк,
  `http.server`), implements `/v1/embeddings`: вектор 768 dims =
  sha256-сидированный PRNG от нормализованного текста (тот же текст → тот же
  вектор; разные тексты → почти ортогональны). mem0 подключается штатно
  (embedder provider=openai, base_url=127.0.0.1:<stub-port>). Никаких
  скачиваний моделей, полная детерминированность.
- Vector store: qdrant-local (штатная зависимость mem0) во временном
  каталоге; **history_db_path — тоже во временный каталог** (собственный
  урок H5: живые каталоги не трогаем).
- Конфиг-ассерт: скрипт печатает `CONFIG_SHA256` через
  `evals/config_fingerprint.py`-механику (announce) и вкладывает
  `config_effective` в JSON-отчёт.

## 3. Сценарий (основной)

1. Три пользователя: `u_A`, `u_B`, `u_C`; каждому — 6 фактов с
   уникальными маркерами-сущностями (имена/цвета/числа, встречающиеся ТОЛЬКО
   у своего пользователя; наборы дизъюнктны по построению).
2. Записи ЧЕРЕДУЮТСЯ: A1, B1, C1, A2, B2, C2, … (интерливинг ловит
   пакетные/кэшевые утечки).
3. Чтение после всех записей, для каждого пользователя:
   - **search**: 3 запроса на собственные факты (top_k=5,
     filters={user_id}) → каждый найденный айтем проверяется на
     принадлежность чужому набору (точное/подстрочное совпадение с чужими
     маркерами);
   - **get_all**(filters={user_id}) → та же проверка;
   - **канал истории**: прямой SQL к temp history db (read-only):
     `messages` и `history` — 0 строк, где `session_scope='user_id=u_X'` И
     контент содержит чужой маркер (проверка обеих таблиц, обеих сторон);
     плюс симметрия счётчиков строк по scope.
4. Счётчики утечек по каналам и направлениям: `search_leaks`,
   `get_all_leaks`, `history_rows_leaks` — все обязаны быть 0.

## 4. Позитивный контроль (тест обязан уметь падать)

Тот же сценарий, но все факты трёх «пользователей» пишутся под ОДИН
общий user_id (`u_shared`), а проверка ведётся теми же детекторами
чужих маркеров: **контроль ОБЯЗАН покраснеть** (leak-счётчики > 0 по
search/get_all). Если контроль зелёный — детектор сломан, `passed=false`
независимо от основного сценария. Это — негативный контроль детектора
(«red self-test» по канон-паттерну GATE GREEN → RED).

## 5. Демонстрация нашего инцидента — ОТДЕЛЬНО, НЕ в вердикте о mem0

Второй изолированный сценарий в том же скрипте, помечен
`section: "our-stand-incident (H5 rationale), NOT a mem0 verdict"`:

- один user_id `u_demo`, две «сессии», ОБЩИЙ history_db_path (как на нашем
  стенде до `ffb5879`);
- после записи сессии-1 и сессии-2 показать: scope `user_id=u_demo` видит
  хвост-10 сообщений обеих сессий (SQL: состав rows по scope; при
  infer=False — уровень хранилища, канал продемонстрирован без LLM);
- вывод-подпись: это канал ВНУТРИ одного scope — mem0 изолирует scopes
  корректно (чужой user_id этих строк не видит — см. основной сценарий);
  утечка была ошибкой нашей интеграции (отсутствие изоляции сессий одного
  пользователя), и именно этот класс ловит H5-гард. Тезис для релиза:
  «mem0 изолирует пользователей; наша интеграция не изолировала сессии —
  пока не появился H5».

## 6. Выход

JSON `p4_mem0_isolation_report.json`:
- `passed` (bool) = основной сценарий 0-утечен И контроль покраснел;
- `leaks`: per-channel per-direction счётчики (search/get_all/history_rows);
- `positive_control`: {fired: true|false, expected: true};
- `our_stand_incident_demo`: {channel_shown: true|false} — вне вердикта;
- `environment`: uname, python version, `pip freeze | grep -i mem0`,
  mem0 pin, config_sha256 + config_effective (config-ассерт);
- `stand`: `<OS, CPU-only, embedder-stub-sha256>`.

## 7. Вердикт (метки глоссария; только после запуска)

Формат: **«verified on mem0@0724291b, <stand>»** — поведенческий вердикт
по глоссарию (executed evidence), с оговоркой границ: проверены каналы
search/get_all/history-rows при infer=False и stub-эмбеддере; extraction-
промптовый путь (LLM) не проверялся. Внешний эксперт может повторить:
`pip install` пина + один скрипт + stub — без нашего стенда, GPU и ключей
(autonomy-требование Way).

## 8. NOT included

- Запуск (только после ревью владельца и санкции);
- любые утверждения о генеративном канале (infer=True) — отдельный класс,
  вне рамки P4;
- правки канона: документ — proposal, в канон — через ADMISSION_CRITERIA
  после прогона и ревью.
