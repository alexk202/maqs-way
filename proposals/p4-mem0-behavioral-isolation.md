# P4: поведенческий тест кросс-пользовательской изоляции mem0 (v0.2, NOT canon — дизайн на ревью, НЕ запускать)

> Status: design proposal v0.2 (owner amendments 26.10 incorporated), for
> owner review. NOT canon, NOT run. Рамка (Совет 26.10): утечка 25.10 —
> дефект НАШЕГО стенда, НЕ mem0; P4 проверяет изоляцию МЕЖДУ субъектами.
> v0.1 → v0.2: добавлены мутационный контроль (п.4b), враждебный запрос с
> own_recall (п.3b), измерения по всем трём ключам scope (п.3), замер
> run_id-изоляции хвоста истории в демо инцидента (п.5), секция observed
> behavior для get/update/delete по чужому ID (п.8, вне вердикта).

## 1. Цель

Доказать поведренчески (исполняемым тестом на чужой системе), что mem0@0724291b
изолирует субъекты по всем каналам чтения и по всем ключам scope:

- **search** (векторный путь, фильтр ДО top-k — см. враждебный запрос);
- **get_all** (перечисление);
- **канал истории / last-messages** (таблицы messages/history ключуются
  session_scope; чужой scope не видит ни строк, ни extraction-хвоста).

Ключи scope (минимум один полный сценарий на каждый): **user_id, agent_id,
run_id**. Ожидание по всем каналам и ключам: **чужого 0 во все стороны**.

## 2. Стенд-инвариант: без LLM, детерминированно, CPU

Без изменений против v0.1: пин `mem0ai/mem0@0724291b`, **infer=False**
(raw-добавления, extraction-LLM не вызывается), **stub-эмбеддер**
(один файл: sha256-сидированные 768-dim векторы, тот же текст → тот же
вектор; mem0 подключается штатно как openai-совместимый), qdrant-local и
history_db во временных каталогах, config-ассерт
(`CONFIG_SHA256` через announce-механику в отчёт).

## 3. Основной сценарий — по три субъекта на каждый ключ scope

Для каждого ключа K ∈ {user_id, agent_id, run_id} отдельный полный
сценарий: три субъекта (K_A, K_B, K_C) с дизъюнктными маркер-фактами
(6 на субъекта), записи чередуются (интерливинг), затем чтение:

- **search**: 3 запроса на собственные факты (top_k=5) → каждый айтем
  проверяется на чужие маркеры;
- **get_all** → та же проверка;
- **канал истории**: read-only SQL к temp history db — 0 строк в scope
  субъекта с чужими маркерами (обе таблицы), симметрия счётчиков;
- счётчики `search_leaks / get_all_leaks / history_rows_leaks` per key per
  direction — все обязаны быть 0.

### 3b. Враждебный запрос (фильтр до top-k)

Для каждой пары (X, Y) и каждого ключа: запрос под X с текстом,
**дословно равным чужому факту Y**. Ожидания:

- **foreign_count = 0** (чужой факт отфильтрован);
- **own_recall > 0** — в выдаче присутствуют СОБСТВЕННЫЕ айтемы X
  (top-k набирается из своего scope, фильтр применён ДО top-k, а не после).
  Пост-фильтрация после глобального top-k дала бы пустую/тощую выдачу
  (чужой近-идентичный айтем занял бы слоты) — дискриминатор ловит порядок.

Счётчик **own_recall** — в отчёт (per key per subject).

## 4. Позитивные контроли (два, оба обязаны покраснеть)

- **(a) shared-id — проверка детектора** (v0.1): те же маркер-факты трёх
  «субъектов» пишутся под ОДИН общий ключ; те же детекторы чужих маркеров
  ОБЯЗАНЫ сработать (leak > 0 по search/get_all). Зелёный = детектор сломан,
  `passed=false` независимо от остального.
- **(b) МУТАЦИОННЫЙ контроль — проверка основного сценария**: в процессе
  теста обернуть mem0-методы поиска так, чтобы **ключ scope выпадал из
  построения фильтра** (обёртка над `Memory.search`/`get_all`, выкидывающая
  ключ из filters перед вызовом оригинала — симуляция класса бага
  «фильтр потерялся»). **Основной сценарий под мутацией обязан
  покраснеть**: search_leaks > 0 (векторный поиск без фильтра возвращает
  чужие маркеры). Если мутация не краснеет — тест не ловит сам класс
  утечки, `passed=false`.

## 5. Демонстрация нашего инцидента — ОТДЕЛЬНО, НЕ в вердикте о mem0

Один user_id `u_demo`, общий history db (как наш стенд до `ffb5879`), без
LLM (infer=False — уровень хранилища):

- **(i) тот же scope**: две сессии без run_id → scope `user_id=u_demo`
  видит хвост-10 обеих сессий (SQL: состав rows) — канал показан;
- **(ii) замер run_id-изоляции хвоста**: те же две сессии, но с **разными
  run_id** → session_scope-строки различаются (`user_id=…&run_id=q1` vs
  `q2`); измерить: видит ли scope сессии-2 строки сессии-1. Гипотеза для
  замера: mem0-нативная изоляция per-question-хвоста через run_id
  (потенциальная альтернатива/дополнение нашего per-question history_db —
  кандидат-заметка для runner-семейства; H5 остаётся, выбор — наш).
  Результат записывается как измерение (изоляция есть/нет), не как вердикт
  о mem0.

Подпись секции: канал живёт ВНУТРИ одного scope — это класс нашего
инцидента (отсутствие изоляции сессий одного пользователя), который ловит
H5; тезис релиза: «mem0 изолирует субъекты; наша интеграция не изолировала
сессии — пока не появился H5».

## 6. Выход

JSON `p4_mem0_isolation_report.json`:
- `passed` = все три ключа: 0 утечек по всем каналам И hostile: foreign=0,
  own_recall>0 И контроль (a) сработал И контроль (b) сработал;
- `leaks`: per key (user_id/agent_id/run_id) per channel per direction;
- `hostile`: per key per pair {foreign_count, own_recall};
- `positive_control_shared_id`: {fired: true|false, expected: true};
- `mutation_control`: {fired: true|false, expected: true};
- `our_stand_incident_demo`: {channel_shown, run_id_isolates_tail};
- `observed_behavior`: (п.8) — вне вердикта;
- `environment`: uname, python, `pip freeze | grep -i mem0`, пин,
  config_sha256 + config_effective; `stand`-метка.

## 7. Вердикт (метки глоссария; только после санкционированного запуска)

**«verified on mem0@0724291b, <stand>»** — поведенческий вердикт по
глоссарию (executed evidence) с границами: каналы search/get_all/history-rows
при infer=False и stub-эмбеддере; три ключа scope; враждебный запрос
подтверждает фильтр-до-top-k; extraction-промптовый путь (LLM) не проверялся;
observed-behavior секция (п.8) в вердикт не входит.

## 8. Observed behavior (опциональная секция, БЕЗ вывода о дефекте, вне вердикта)

get/update/delete по ID чужой записи: для тройки субъектов основного
сценария — попытки `get(memory_id)` / `update(memory_id, …)` /
`delete(memory_id)` с ID записей чужого субъекта; всё происходящее
записывается как наблюдаемое поведение (вернул/изменил/удалил/ошибка), в
отдельной секции отчёта; никаких суждений о дефекте — только факты для
будущих пакетов (кандидат в отдельный тест-дизайн по санкции).
