## 1. Слой ПРИНЦИПОВ

**Структура каждого принципа (паттерн P/V/E применён к этому слою с v0.1.1; слои «Архитектура» и «Верификация» выравниваются по тому же паттерну в v0.2):**
- Свойство (обязательно): что должно выполняться
- Верификация (how to check): тест, метрика, негативный сценарий
- Пример (не нормативно, hint): подсказка
- Ссылка на MAQS + инцидент (родословная MAQS → Way)

> Пороговые значения в этой версии — **ориентировочные инженерные цели, подлежат пересмотру после первого прогона на реальной системе**. Нормативные пороги — в v0.2.

### P1 Достоверность (Veracity) — память это данные, а не инструкции

- **Свойство:** Каждая запись памяти — типизированные данные, а не исполняемая инструкция. Вывод модели типизируется как `source.type=model_output` и не должен повышать доверие при суммаризации/преобразовании.
- **Верификация:** Зонд ложных фактов OWASP ASI06-001 → Policy Broker BLOCK 100% (ориентировочно). Обёрнут в `<retrieved_context type=...>`. Преобразование должно сохранять `confidence_after ≤ confidence_before` для model_output.
- **Пример:** `огороженный retrieved_context + policy broker BLOCK`
- **Ссылка на MAQS:** E6 (эскалация доверия при суммаризации), F1–F8 петля обратной связи, F7 admitted≠trusted. **Инцидент:** агент суммаризировал собственный отчёт об ошибке и повысил доверие с 0.6 до 0.9, что привело к петле.

### P2 Провенанс (Provenance) — каждая запись прослеживается

- **Свойство:** Каждая запись несёт: кто создал, когда, ссылка+хеш источника, policy_id/версия, доверие, история преобразований. Мутации дописывают провенанс, никогда не заменяют происхождение.
- **Верификация:** Валидация схемы против OMPS memory-item.schema.json, расширенного обязательной привязкой OAMP §4.3 `source.agent_id == provenance.created_by.id`. `identity_signature` = Ed25519 над каноническим JSON (спецификация перенесена в v0.2, см. Бэклог §6.2).
- **Пример:** провенанс OMPS + agent_id, session_id, source_hash из OAMP
- **Ссылка на MAQS:** B (целостность записи), 0 Map. **Инцидент:** осиротевшие векторы без источника после миграции — аудит невозможен.

### P3 Управляемое старение (Controlled Aging) — забывать устаревшее, сохранять релевантное

- **Свойство:** Память затухает по устареванию, обновляется при использовании, замещается при противоречии, истекает по TTL — не вытесняя релевантное.
- **Верификация:** Golden set: временнáя точность CI gate ≥65%, target ≥80% (LoCoMo temporal + Graphiti valid_at); точность обновления знаний после замещения ≥70% (LongMemEval); свежее не вытесняется раньше устаревшего.
- **Пример:** битемпоральность Graphiti `valid_at/invalid_at` (когда факт был истинен) + `t_created/t_expired` (когда узнали)
- **Ссылка на MAQS:** D Retrieval, C Growth. **Инцидент:** удвоение объёма после того, как job затухания удалил свежие факты из-за путаницы с временными метками.

### P4 Изоляция (Isolation) — границы доказываются негативными тестами

- **Свойство:** Границы тенантов/пользователей/проектов/агентов соблюдаются, включая путь векторного поиска, — а не только наличие фильтра.
- **Верификация:** Негативный тест `cross_tenant_retrieval_returns_0`, leak=0 (ориентировочно). Включая векторный путь. Должен покрывать провенанс эмбеддингов. G1 требует 4 фикстуры (§2.3): независимые caller'ы, неверный/отсутствующий scope, попытка записи read-only, доступ после отзыва.
- **Пример:** инвариант №1 MemoryOps + модель областей AMSP
- **Ссылка на MAQS:** G Isolation. **Инцидент:** поиск вернул память Пользователя A Пользователю B, потому что фильтр pgvector применялся после top-k.

### P5 Удаляемость (Deletability) — удаление распространяется везде

- **Свойство:** Удаление распространяется на реплики, векторные индексы, кэши, производные сводки. Надгробие (tombstone) сохраняется без персональных данных.
- **Верификация:** Решётка удаления LOGICAL/PHYSICAL/SEMANTIC/MODEL, остаток 0.0% (ориентировочно; бенч tombstone). Удаление = каскад из 6 уровней `graph_edges → nodes_if_sole_provenance → embeddings_fk → facts_fk → artifacts → rounds` в одной PG-транзакции + best-effort сверка графа. `каскад только при sole provenance` — если провенанс НЕ единственный, удаляется ребро, узел сохраняется.
- **Пример:** deletion_log(request_id, timestamp, scope, layer_counts, requestor) с подписью Ed25519, hash-цепочкой, layer_counts для аудита
- **Ссылка на MAQS:** B, G. **Инцидент:** GDPR-удаление убрало строку, но rebuild survivors в Qdrant сохранил эмбеддинг восстановимым на 100%.

### P6 Восстановимость (Recoverability) — бэкап + проверенное восстановление

- **Свойство:** Бэкап, версионирование схем/эмбеддингов, идемпотентные миграции, проверенные процедуры восстановления.
- **Верификация:** Restore drill ежеквартально, равенство хешей восстановленного хранилища и манифеста бэкапа. Проверка совместимости эмбеддингов: модель версионирована, несовпадение → fallback только на ключевые слова `retrieval_mode=fallback`.
- **Пример:** бэкап MAQS P1 + версионированная модель эмбеддингов
- **Ссылка на MAQS:** H, I. **Инцидент:** обновление модели эмбеддингов — все старые векторы не совпали, retrieval молча вернул пустоту без алерта.

### P7 Переносимость (Portability) — память пользователя принадлежит пользователю

- **Свойство:** Память пользователя экспортируется/импортируется без преобразований, с сохранением согласий, чувствительности и провенанса.
- **Верификация:** Round-trip `export→import` → 0 потерь полей provenance + consent, равенство хешей. Использует OMPS memory-bundle.schema.json + export/import AMSP.
- **Пример:** bundle OMPS
- **Ссылка на MAQS:** Новое, из OMPS/AMSP. **Инцидент:** экспорт стёр хеш источника, импорт создал дубликат с новым id.

### P8 Измеримость (Measurability) — доказать, что работает, а не что механизм существует

- **Свойство:** Качество измеряется на репрезентативных задачах, включая негативные случаи.
- **Верификация:** Eval-обвязка LoCoMo/LongMemEval/MemoryAgentBench + негативные сценарии cross_tenant_leak, prompt_injection_via_memory, feedback_contamination, stale_overrides_fresh, shared_fact_visibility_leak. Метрики ориентировочны до первого прогона (CI gate / target): R@5 ≥0.7 / ≥0.85, abstention ≥0.8 / ≥0.9 при отсутствии свидетельств, duplicate ≤5% / ≤2%, contamination ≤1% / 0%.
- **Пример:** Golden set + LLM-judge + R@k + описание ограничений (чего метрика не видит)
- **Ссылка на MAQS:** D9 расширенный (D9 = самоотчётная диагностика агента, см. MAQS D9). **Инцидент:** D9 существовал, но без поведенческого теста — система прошла чек-лист и провалила временный recall в проде.


## 2. Слой АРХИТЕКТУРЫ — какие свойства должны быть реализованы

### 2.1 Модель данных

Канонической является схема OMPS. Поле `schema_version` объясняет провенанс. `status` — производное представление событий жизненного цикла (см. §2.2), а не хранимое поле:

  "id": "mem_001",
  "type": "preference | episode | semantic | procedural | project | system",
  "subject": {"type": "user | agent | team | org | system", "id": "user_123"},
  "scope": {"type": "user-portable | agent-private | team-shared | org-shared | local-session"},
  "content": {"format": "text/plain", "value": "...", "language": "en"},
  "sensitivity": "low | medium | high | secret",
  "consent": {
    "basis": "explicit_user_request | inferred | imported",
    "exportable": true,

  "provenance": {

    "created_by": {"type": "agent", "id": "agent_001"},
    "source": {"type": "conversation | file | web | agent | model_output", "ref": "conv_123", "hash": "sha256:..."},

    "visible_to": ["user_123", "agent_001"]
  },
  "embedding": {"model": "qwen3-1024", "version": "1.0", "derived_from_trust": "low", "vector_id": "..."},
  "revision": 3,

**Примечание:** deletion_marker — НЕ поле живой записи; это отдельный артефакт, управляемый схемой OMPS `deletion-marker.schema.json`, создаваемый только в момент удаления и сохраняемый в governance tombstone (структура: `request_id, timestamp, scope, layer_counts, requestor, signature: ed25519:...`). Показан в примере P5 только для наглядности схемы.

**Примечания к модели данных:**
- **schema_version:** `"omps-0.1.0+way-v0.1.3"` — база `omps-0.1.0` + расширение `way-v0.1.3`, семантика semver-расширения задокументирована.
- **status:** производное представление событий жизненного цикла (§2.2), не хранимое поле — вычисляется как проекция последнего события жизненного цикла записи.
- **identity_signature:** убрано из примера живой записи; спецификация (Ed25519 над каноническим JSON) перенесена в v0.2 — см. Бэклог §6.2.
- **Нотация scope:** допускаются оба варианта `user.portable` и `user-portable` — каноничен `user-portable` (AMSP), таблица соответствий в `docs/mapping-to-maqs.md`.
- **visible_to:** массив `subject.id`, для которых запись видима. Механизм семантического маскирования (§2.2): при удалении общего факта запросивший удаляется из `visible_to`; пустой массив → физическое удаление. Отсутствие `visible_to` = без ограничений внутри scope.
- **Битемпоральность vs retention:** `valid_at/invalid_at` = когда факт был истинен в мире (Graphiti), `retention.valid_from/valid_to` = когда мы его храним. Приоритет: мировое время — для рассуждений, retention-время — для жизненного цикла. См. §2.2 *Приоритет времён*.
- **legal_hold:** добавлено в retention для Профиля B, где Delete неисполним в период удержания.

### 2.2 Жизненный цикл

Машина состояний полная:

ACTIVE → STALE (затухание) → ACTIVE (обновление)
ACTIVE → CONTESTED (конфликт) → SUPERSEDED (разрешение, политика: для Профиля A побеждает пользователь, для B — Policy Broker, для C конфликта нет)
ACTIVE/STALE → EXPIRED (истечение TTL по политике) → ARCHIVED (мягкий архив, смена состояния, не физическое удаление)
ARCHIVED → ACTIVE (восстановление, если recoverable и политика позволяет)
Any → DELETED (удаление пользователем / GDPR Art17, кроме legal_hold) → TOMBSTONE (мягкое: контент+эмбеддинг очищены, governance tombstone сохранён) → null (жёсткая компакция, подпись Ed25519)

Если провенанс единственный: узел удаляется, иначе удаляется ребро.

Политика разрешения конфликтов:
- Персональный ассистент: побеждает пользователь (User Wins), новый факт замещает оспоренный со ссылкой `supersedes`.
- Корпоративный: Policy Broker решает `decision: SAVE|PENDING_APPROVAL|BLOCK|DROP_LOW_UTILITY` + `mode: APPEND|UPDATE_EXISTING|MERGE_WITH_EXISTING` (два ортогональных поля). Решение брокера обжалуется: оспоренные записи могут быть переданы на человеческое рассмотрение; исход обжалования дописывает провенанс и никогда не переопределяет запись брокера молча. Роль рассматривающего человека = `operator` (определена в §2.3; полная матрица прав operator — TODO v0.2).
- Эфемерный: записи нет — конфликтов нет.

**Приоритет времён.** При расхождении мирового времени (`valid_at`/`invalid_at`) и времени хранения (`retention.valid_from`/`valid_to`) разрешение следует каноническому алгоритму из `maqs-way-standard.json` → `lifecycle.temporal_priority_algorithm` (5 шагов) — здесь не дублируется во избежание рассинхрона. Кратко:
- `legal_hold` блокирует удаление независимо от мирового времени
- retention истёк (`retention.valid_to < now`) → `EXPIRED`
- мировое время говорит, что факт уже не истинен (`invalid_at < now`) → `EXPIRED` — **не** `SUPERSEDED`; замещение — исход разрешения конфликтов (см. машину состояний выше), а не автоматический эффект времени
- иначе `ACTIVE`/`STALE` по затуханию
- фильтр рассуждений: retention валиден И `valid_at ≤ now` И (`invalid_at` null или `> now`)

### 2.3 Контроль доступа

- Модель областей из AMSP формализована, канон `user-portable` и т.д.
- Policy Broker разделён: `decision: SAVE|PENDING_APPROVAL|BLOCK|DROP_LOW_UTILITY` + `mode: APPEND|UPDATE_EXISTING|MERGE_WITH_EXISTING` — ортогональны.
- **Роль operator:** человек, который рассматривает эскалированные/обжалованные решения брокера и оспоренные записи. Может читать оспоренные записи и подтверждать/переопределять исходы обжалований; каждое действие дописывает провенанс. Полная матрица прав — TODO v0.2.
- **SLA operator:** рассмотрение в течение 72ч для эскалированных/обжалованных решений и оспоренных записей в Профиле B (рекомендация, не глобальное нормативное требование).
- **Фикстуры G1 (обязательны, MAQS G1 [CRIT]):** граница доказывается попытками нарушений, а не наличием фильтра: (1) независимо аутентифицированные caller'ы A vs B, (2) неверный или отсутствующий scope, (3) read-only caller пытается писать → BLOCK, (4) доступ после отзыва членства → BLOCK. Односкоповый pass-through границей не является.

### 2.4 Сборка контекста

- MAQS E: слепая усечка запрещена, бюджеты, позиционирование
- Content-as-Data: весь полученный контент огорожен `<retrieved_context>` с типизацией, не инъецируется как инструкции (OWASP LLM08)
- Защита от загрязнения обратной связью: model_output → ingestion только через Extractor + проверка secret/PII + policy broker, иначе BLOCK
- **Потолок F8 (MAQS F8):** записи с `source.type=model_output` не могут получать важность выше заданного потолка до подтверждения внешним источником или пользователем.
- **Приоритет артефакта E12 (MAQS E12):** текущий артефакт сохраняет фактический приоритет над памятью; конфликт остаётся наблюдаемым, память не должна молча подменять или реконструировать представление артефакта.

`alive` и `critical` — поля расширения профиля (см. `extensions`
в maqs-way-standard.json); они не входят в ядро модели данных
(`schema_version way-v0.1.3`, заморожена).


**E10 — Квота живой памяти ([REC], MAQS E10).** Квота действует
по-скоупно-по-субъектно: отдельно в каждом скоупе для каждого субъекта
(якорь скоупа — `scope_enum` в maqs-way-standard.json), не глобально.
Эффект: `alive: true` освобождает запись от распада и суммаризации, пока
флаг установлен; НЕ блокирует удаление (удалением управляет retention =
`"legal_hold"`). Поведение при переполнении (по умолчанию): новая защита
ОТКЛОНЯЕТСЯ (fail-closed для защиты), событие логируется как
`cap_overflow {subject, scope, cap, attempted_id}`;
`escalate_after_denials` подряд отказов эскалируются владельцу
(советующий, поскольку E10 [REC]). У `escalate_after_denials` нет
значения по умолчанию — она ОБЯЗАНА быть объявлена каждой системой,
включающей квоту. Система НЕ ДОЛЖНА молча снимать существующие защиты и
НЕ ДОЛЖНА молча отклонять новые: FIFO-вытеснение по умолчанию оставляет
`alive: true` при фактически снятой защите — декларация переживает факт
(silent-fail, класс B5); лживый флаг хуже забвения. Только по явному
opt-in: `overflow: evict_oldest` — явная конфигурация на систему; каждое
вытеснение ОБЯЗАНО логироваться с id записи и причиной (без тишины даже
при opt-in). Opt-in явно переопределяет семантику `alive` (приоритет
политики, а не абсолютная защита) и потому не является ложью. Нарушения
квоты измеримы (`alive_cap_overflow_rate`, паттерн P8), но не блокируют.


**E10 — alive vs legal_hold (ортогональность).** `legal_hold` и `alive`
— ортогональные механизмы: `legal_hold` (существующее значение retention
`"legal_hold"`) блокирует удаление (уровень управления, жёсткий);
`alive` защищает от распада и суммаризации (уровень значимости, [REC]).
Запись может нести оба одновременно; ни один не влечёт другой. Hold не
даёт alive-защиты и наоборот; снятие одного никогда не снимает другой.
Проверка: `is_forgettable(r) = not r.alive and r.retention !=
"legal_hold"`.


**E11 — Декларируемые критические метки ([IMP], MAQS E11).** Критичность
— явная метка с провенансом (источник: владелец или авторизованный
процесс). Автоматический вывод важности отсутствует: `importance` в
каноне — потолок F8 (ограничение), а не поле модели — без шкалы, порогов,
источника. Непомеченные записи трактуются как некритичные (без
переупорядочивания, без угадывания); `unlabeled_ratio` измеряется, чтобы
разрыв оставался видимым. Непомеченные блоки дают явный лог
(«0 критических блоков»), никогда — молчаливый проход с угадыванием.


**E11 — Проверка позиционирования.** `E11.verify_placement(context)` —
структурный аудит (без LLM): каждый блок с меткой «критический» ОБЯЗАН
занимать head- или tail-зону (первые/последние `critical_zone_fraction`
токенов собранного контекста, умолчание 0.15; owner: E11; калибровка →
список v0.4); критический блок в средней зоне = FAIL. Семантическая
адекватность размеров зон — отложено (список v0.4).


Глоссарий (заморожен; переопределение — только отдельной санкцией):
`alive`/`protected` — декларируется, не выводится; `critical` — явная
метка с провенансом (декларируется, не выводится); `head`/`tail-зоны` —
первые/последние `critical_zone_fraction` токенов собранного контекста;
`unlabeled_ratio` — отчёт, не гейт; «positioning» здесь — процедура
размещения критических блоков (head/tail-зоны + позиционный аудит), а не
голое слово.

### 2.5 Устойчивость

- Контракты между хранилищами, версионирование схем/эмбеддингов, идемпотентные миграции
- Провенанс эмбеддингов: `embedding.derived_from_trust` наследуется от источника, эмбеддинг НЕ «очищает» происхождение
- **D8 несовместимые эмбеддинги (MAQS D8 [CRIT]):** несовпадение размерности/языка → явный отказ с диагностикой, а не всплеск предупреждений при поиске; перед смешанным поиском — переиндексация или миграция.
- **H5 изоляция тестов (MAQS H5 [CRIT]):** тесты используют временные/in-memory хранилища и моки API, никогда не пишут в живую память; изоляция покрывает файловую систему (без продовых путей по умолчанию); guard-проверка до/после подтверждает отсутствие утечек тестовых артефактов.

### 3.3 Решётка верификации удаления

- LOGICAL: search() возвращает 0
- PHYSICAL: DELETE+REINDEX+VACUUM FULL pgvector, rebuild survivors Qdrant, ноль HNSW-слотов Chroma — проверяется сканом файлов

Каждый уровень — квитанция с подписью Ed25519, воспроизводимая. Deletion_log без персональных данных.

### 3.4 Логирование

- Что логировать (Art12/19): период использования начало/конец, проверенная reference DB, ввод, приведший к совпадению, задействованные физлица, идентичность агента, policy_version, классификация, исход, точная временная метка, подпись
- Как: OTel GenAI `gen_ai.operation.name`, `gen_ai.conversation.id`, `gen_ai.tool.name`, `gen_ai.usage.*`, `gen_ai.client.inference.operation.details` (PII — opt-in)
- **Санитизация (ужесточено):** `gen_ai.client.inference.operation.details` — разрешено: `tool_args_sanitized`, `retrieval_count`, `policy_decision`, `latency_ms`; запрещено: `raw_content`, `secret`, `PII`, `embedding_vector`. Фильтр secret/PII применяется до логирования, то же правило, что у Policy Broker. Включая credential-in-URL (`?token=...`, `bot<id>:AA...` в пути) — маскируется редактором до записи (MAQS I13 [CRIT]).
- Защита от подделки: hash-цепочка, Ed25519, WORM lock для регулируемых тенантов, retention 12 месяцев по умолчанию, 6 лет настраиваемо для регулируемых (источник: EU AI Act Art12 задаёт минимум 6 месяцев, Way расширяет для регулируемого Профиля B, задокументировано). Примечание: фиксация до возврата ответа добавляет latency ~5-15мс.
- Источники упомянуты в соответствии со своими лицензиями.

`threshold`, `window {type, size}`, `action` и ключи равенства классовых
счётчиков ниже — настройки расширения политики (см. `extensions.policy`
в maqs-way-standard.json); они не входят в ядро модели данных
(`schema_version way-v0.1.3`, заморожена). Журналы алертов и записи
эскалаций переиспользуют существующую инфраструктуру логирования
(hash-цепочка, retention по `logging.retention`); новых полей модели
данных не вводится.

Каждый классовый счётчик объявляет ТРИ независимых литерала (никогда не
склеенных): threshold N, window {type, size}, action. Порог и окно
настраиваются независимо. Типы окон: `sliding` (события внутри
скользящего окна) | `tumbling` (фиксированные корзины); `sliding` — тип
окна по умолчанию, `tumbling` требует явного объявления на деплоймент.
Каждый счётчик объявляет свой ключ равенства (сигнатуру): без ключа
«идентичные» не определены, счётчик недетерминирован — такой счётчик
отвергается.

**I10 — Бюджет шума ([IMP], MAQS I10).** Объявленные параметры (owner:
I10): `threshold` 3 (умолчание), `window` {sliding, 5m} (умолчания),
ключ равенства «warning text», `action` «aggregate». Одно и то же
предупреждение, повторённое N+ раз за интервал, агрегируется счётчиком —
N идентичных предупреждений становятся одной записью + счётчиком; после
порога поодиночке не выдаются; после N идентичных предупреждений —
дедуплицировать или эскалировать на другой уровень. B5-связка: заявленный успех без
выполненной работы — отказ класса B5, обнаруживается как чистая функция
от (claimed_events, performed_actions) над объявленным `work_sink`
(зафиксированные побочные эффекты; нет умолчания — ОБЯЗАН быть объявлен
при применении проверки, owner: I10); заявленный успех + пустой
приёмник → RED. I10 существует, чтобы дублирующий шум не маскировал
ложный успех.

**I11 — Цикл восстановления ([CRIT], MAQS I11).** Объявленные параметры
(owner: I11): `threshold` 3 (умолчание), `window` {sliding, 10m}
(умолчания), ключ равенства «exit code», `action` «halt+alert». Любой
автоматический рестарт (systemd/supervisor/self-heal) сопровождается
диагностическим следом первопричины. Цикл восстановления без диагноза
запрещён: после N повторов без диагноза — halt и alert, никогда не
вечный рестарт. Halt останавливает СОБСТВЕННЫЙ процесс; halt-без-alert
запрещён ровно так же, как restart-без-диагноза. Приёмник алертов —
РЕАЛЬНОЕ персистентное хранилище (журнал-файл / syslog; нет умолчания —
ОБЯЗАН быть объявлен, должен читаться после halt, owner: I11), никогда
не голые stderr/exit code: stderr не переживает halt, exit code виден
только родителю. Алерт, который нельзя прочитать после halt, —
silent-fail (класс B5). Верификация читает след ПОСЛЕ halt из приёмника.

**I12 — Бюджет эскалации ([CRIT], MAQS I12).** Объявленные параметры
(owner: I12): `threshold` 3 (умолчание), `window` {sliding, 1h}
(умолчания), ключ равенства «dependency + error code», `action`
«escalate». Повторяющийся отказ зависимости с идентичной сигнатурой
эскалируется после N вхождений (alert / halt / flagged degradation) —
никогда не опрашивает бесконечно. Escalate адресован ВНЕШНИМ
зависимостям (нет права останавливать, только голос) и ПОВТОРЯЕМ по
расписанию — контракт уведомлений, а не одиночный выкрик; расписание
повторов не имеет умолчания и ОБЯЗАНО быть объявленным (owner: I12).
Эскалация без записи в журнале — отказ класса B5 (тот же класс, что
halt-без-alert). Система, знающая об отказе и не эскалирующая,
деградирует молча.

**Граница halt / escalate.** Halt применяется к собственному процессу
(право остановить = обязанность подать alert); escalate — к внешним
зависимостям (нет права останавливать, только голос). При конфликте
(выполнены оба условия): halt доминирует (безопасность) + escalate
владельцу. `flagged degradation` ОБЯЗАН быть наблюдаемым в приёмнике —
иначе деградация молчалива = B5.

Смежное, не покрывающее: SPEC §2.3 (appeal-эскалация + SLA оператора)
делит только словарь (другой триггер, другой механизм); закрытие этого
gap'а словами «уже есть в §2.3» отвергается заранее.

Отложено (список v0.4): per-scope/per-subject разбиение счётчиков (ср.
семантика квоты E10); переход деплойментов на tumbling-окна.

Глоссарий (заморожен; переопределение — только отдельной санкцией):
`policy triple` — threshold + window {type, size} + action, три
независимых литерала, никогда не склеенных; `equality key` (сигнатура) —
объявленное поле, определяющее «идентичные» события; `work_sink` —
объявленное хранилище зафиксированных побочных эффектов; `alert sink` —
персистентное хранилище, держащее halt-алерт и читаемое после halt;
`halt` — остановка собственного процесса; `escalate` — контракт
уведомлений внешним зависимостям, повторяемый по объявленному
расписанию.

Требования к реакции для проверенных исключений ниже —
настройки расширения политики (см. `extensions.policy` в
maqs-way-standard.json); они не входят в ядро модели данных
(`schema_version way-v0.1.3`, заморожена). Словарь получателей
переиспользует канонические роли `owner` и `operator`; новых полей
модели данных не вводится.

**I14 — Реестр обработчиков ([REC], MAQS I14).** Если класс исключения
проверен (пойман и перевыброшен или залогирован), но не имеет
зарегистрированного обработчика или пути эскалации, проверка
неполна — обнаружение без реакции не является покрытием. Каждый
проверенный класс ОБЯЗАН иметь реакцию: `handler` и/или
`escalation_path` (минимум одно). `handler` — локальная реакция на
стороне собственного процесса (семейство halt, ср. I11);
`escalation_path` — уведомление владельца/оператора с продолжением в
деградировавшем режиме (внешняя сторона, семейство escalate, ср. I12).
Путь ОБЯЗАН завершаться в объявленном получателе (`owner` или
`operator`); путь-в-пустоту не покрыт — тот же класс, что
halt-без-alert (семейство B5). Handler И path одновременно — ЛЕГАЛЬНО
(handler + запасной path = эшелонированная защита); запрещать
сочетание отвергается. Словарь наследуется от классовых счётчиков
(I10–I12), не переопределяется: halt : escalate :: handler : path;
классы-счётчики, внесённые в реестр, несут reaction = counter
(aggregate / halt+alert / escalate) — определены каноном счётчиков,
здесь упоминаются, двойного владения нет.

**I14 — Объявленный каталог.** Каталог классов — ОБЪЯВЛЕННЫЙ список;
полнота НЕ заявляется и НЕ гейтируется. Строка отчёта «checked N
declared classes; completeness NOT claimed» обязательна; N выводится из
объявленного каталога (без независимого умолчания, owner: I14). Рост —
только явным изменением (коммитом), никогда молча в рантайме; каждый
новый класс входит с источником (инцидент/аудит) и владельцем.

**I14 — Модель вердикта (два уровня, не выбор).** Уровень пробы
(юнит): несогласованность внутри каталога — СТРОГО — класс-сирота (нет
реакции), мёртвый обработчик (зарегистрирован без класса каталога),
путь-в-пустоту → RED; проверка, которая не может упасть, — не
проверка. Уровень гейта (интеграция): находки [REC] —
report-not-failing — агрегатный гейт не блокируется, но каждая находка
ОБЯЗАНА быть НАЗВАНА в отчёте (никогда не сворачивается); [REC]
управляет БЛОКИРОВАНИЕМ, а не вердиктоспособностью. «0 находок» и
«проверка не запускалась» — различимые состояния. Доля покрытия
`handled/probed` — отчёт, не гейт (owner: I14); каждая сирота
перечисляется по имени. Статус [REC] (advisory) переносится в ОТЧЁТЕ,
а не в семантике гейта. I14 не объявляет настраиваемых числовых
параметров: указанные выше числа — производные, отчётные значения.

Отложено (список v0.4): owners_registry / SLA / fallback-схема для
путей эскалации (нет канонического источника шкал SLA); ревизия
каталога tumbling; импорт таксономии исключений.

Глоссарий (заморожен; переопределение — только отдельной санкцией):
`handler` — локальная реакция на стороне собственного процесса;
`escalation_path` — уведомление владельца/оператора с продолжением в
деградировавшем режиме, завершающееся в объявленном получателе;
`orphan class` — проверенный класс без зарегистрированной реакции;
`dead handler` — зарегистрированный обработчик без класса каталога;
`path-into-void` — путь эскалации, чей адресат не является объявленным
получателем; `handled/probed` — доля покрытия, отчёт, не гейт.
