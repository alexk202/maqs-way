## (а) Нормативный текст EN — SPEC.md, раздел «### 2.5 Resilience»
(дописать в конец раздела, после пункта H5; существующий текст не
менять)

---EN BEGIN---
The write-atomicity requirement below is a policy extension setting
(see `extensions.policy` in maqs-way-standard.json); it is not part of
the core data model (`schema_version way-v0.1.3`, frozen). It binds the
§2.5 store contracts to a crash-observability property; failure
observability itself remains with B5 (logging, §3.4).

**B4 — Write atomicity ([IMP], MAQS B4).** Writing to multiple stores
(message + vector + index) is transactional or compensable: partial
writes ("message saved, vector not") are excluded. Atomicity covers ALL
state writes, including append operations and compound file+state
pairs; partial atomicity does not satisfy this item.

The requirement is on the PROPERTY, not on a mechanism: after a crash
at ANY point of a write sequence, a reader observes either the
fully-old state or the fully-new state — never a mixed or partial
state. The choice of mechanism is NOT prescribed. Known mechanisms are
examples, not requirements: a database transaction; an
outbox/compensation scheme (an explicit in-progress intent record +
post-crash recovery that rolls back or completes the interrupted
write); for a single file — write to a temporary file, fsync, atomic
rename, directory fsync. Appends are state writes: an interrupted
append leaves the file exactly as before the attempt (or completes —
never a half-append as the observable final state). A compound
file+state pair is atomic as a unit: the file and its paired state flip
together or not at all.

An explicit in-progress state is part of the requirement wherever
compensation is used: the intent record marks the write as underway so
that recovery after a crash can either roll it back or complete it;
readers treat uncommitted (in-progress) writes as absent. The
in-progress marker is the mechanism's internal state — it does NOT add
a lifecycle state to the data model (§2.1 enum unchanged). Recovery
after a crash MUST run before new writes proceed; the recovery outcome
is logged (B5 discipline, §3.4). Verification injects a crash at every
point between write steps and reads the state after each crash — a
check that cannot fail is not a check.

B4 declares no tunable numeric parameters: the requirement is a
crash-observability property.

Glossary (frozen; redefinition only via separate sanction):
`atomic` — after a crash at any point, a reader sees the old or the new
state in full, never a mixture; `compensable` — an interrupted write is
rolled back or completed by recovery; `in-progress (intent) record` —
the mechanism's internal marker of an underway write, invisible to
readers until commit; `compound file+state pair` — a file and its
paired state flipped as one unit; `append` — a state write covered by
atomicity like any other.
---EN END---

## (б) RU-зеркало — SPEC-RU.md, раздел «### 2.5 Устойчивость»

---RU BEGIN---
Требование атомарности записи ниже — настройка расширения политики
(см. `extensions.policy` в maqs-way-standard.json); оно не входит в
ядро модели данных (`schema_version way-v0.1.3`, заморожена). Оно
привязывает контракты хранилищ §2.5 к свойству наблюдаемости при сбоях;
наблюдаемость самих сбоев остаётся за B5 (логирование, §3.4).

**B4 — Атомарность записи ([IMP], MAQS B4).** Запись в несколько
хранилищ (сообщение + вектор + индекс) транзакционна или компенсируема:
частичные записи («сообщение сохранено, вектор — нет») исключены.
Атомарность покрывает ВСЕ записи состояния, включая операции
дозаписи (append) и составные пары «файл + состояние»; частичная
атомарность этому пункту не удовлетворяет.

Требование — к СВОЙСТВУ, а не к механизму: после сбоя в ЛЮБОЙ точке
последовательности записи читатель наблюдает либо целиком старое
состояние, либо целиком новое — никогда смешанное или частичное. Выбор
механизма НЕ предписывается. Известные механизмы — примеры, а не
требования: транзакция БД; схема outbox/компенсации (явная intent-запись
«в процессе» + восстановление после сбоя, которое откатывает или
завершает прерванную запись); для одного файла — запись во временный
файл, fsync, атомарное переименование, fsync каталога. Дозаписи (append)
— записи состояния: прерванная дозапись оставляет файл ровно таким, как
до попытки (либо завершается — никогда полу-дозапись как наблюдаемое
итоговое состояние). Составная пара «файл + состояние» атомарна как
единица: файл и парное к нему состояние переключаются вместе или
никак.

Явное состояние «в процессе» входит в требование всюду, где
используется компенсация: intent-запись помечает запись как идущую,
чтобы восстановление после сбоя могло её откатить или завершить;
читатели трактуют незакоммиченные (находящиеся в процессе) записи как
отсутствующие. Маркер «в процессе» — внутреннее состояние механизма;
он НЕ добавляет состояние жизненного цикла в модель данных (перечень
§2.1 не меняется). Восстановление после сбоя ОБЯЗАНО выполняться до
новых записей; исход восстановления логируется (дисциплина B5, §3.4).
Верификация инъецирует сбой в каждой точке между шагами записи и читает
состояние после каждого сбоя — проверка, которая не может упасть, — не
проверка.

B4 не объявляет настраиваемых числовых параметров: требование — свойство
наблюдаемости при сбоях.

Глоссарий (заморожен; переопределение — только отдельной санкцией):
`atomic` (атомарно) — после сбоя в любой точке читатель видит старое
или новое состояние целиком, никогда смесь; `compensable`
(компенсируемо) — прерванная запись откатывается или завершается
восстановлением; `in-progress (intent) record` — внутренний маркер
механизма о идущей записи, невидимый читателям до коммита;
`compound file+state pair` — файл и парное состояние, переключаемые как
одна единица; `append` — запись состояния, покрытая атомарностью как
любая другая.
---RU END---
