## (а) Нормативный текст EN — SPEC.md, раздел «### 3.4 Logging»
(дописать в конец раздела; существующий текст не менять)

---EN BEGIN---
`threshold`, `window {type, size}`, `action` and the equality keys of
the class counters below are policy extension settings (see
`extensions.policy` in maqs-way-standard.json); they are not part of the
core data model (`schema_version way-v0.1.3`, frozen). Alert journals
and escalation entries reuse the existing logging infrastructure
(hash-chained, retention per `logging.retention`); no new data-model
fields are introduced.

Every class counter declares THREE independent literals (never glued):
threshold N, window {type, size}, action. Threshold and window are
independently tunable. Window types: `sliding` (events within a trailing
window) | `tumbling` (fixed buckets); `sliding` is the default window
type, `tumbling` requires an explicit per-deployment declaration. Every
counter declares its equality key (signature): without a key, "identical"
is undefined and the counter is nondeterministic — such a counter is
rejected.

**I10 — Noise budget ([IMP], MAQS I10).** Declared parameters (owner:
I10): `threshold` 3 (default), `window` {sliding, 5m} (defaults),
equality key "warning text", `action` "aggregate". The same warning
repeated N+ times per interval is aggregated with a counter — N
identical warnings become one record + count, never emitted individually
past the threshold; after N identical warnings, deduplicate or escalate
to a different level. B5-link: claimed success on unperformed work is a
B5-class failure, detected as a pure function of (claimed_events,
performed_actions) over a declared `work_sink` (recorded side-effects;
no default — MUST be declared when the check is applied, owner: I10);
claimed success + empty sink → RED. I10 exists to prevent duplicate
noise from masking false success.

**I11 — Recovery loop ([CRIT], MAQS I11).** Declared parameters (owner:
I11): `threshold` 3 (default), `window` {sliding, 10m} (defaults),
equality key "exit code", `action` "halt+alert". Any automatic restart
(systemd/supervisor/self-heal) must be accompanied by a diagnostic trace
of the root cause. A recovery cycle without diagnosis is prohibited:
after N repetitions without diagnosis — halt and alert, never eternal
restart. Halt stops the OWN process; halt-without-alert is forbidden
exactly like restart-without-diagnosis. The alert sink is a REAL
persistent store (journal file / syslog; no default — MUST be declared,
must be readable after halt, owner: I11), never bare stderr/exit code:
stderr does not survive halt, exit code is visible to the parent only.
An alert that cannot be read after halt is a silent-fail (class B5).
Verification reads the trace AFTER halt from the sink.

**I12 — Escalation budget ([CRIT], MAQS I12).** Declared parameters
(owner: I12): `threshold` 3 (default), `window` {sliding, 1h}
(defaults), equality key "dependency + error code", `action` "escalate".
A repeated dependency failure with identical signature escalates after
N occurrences (alert / halt / flagged degradation) — never polls
indefinitely. Escalate targets EXTERNAL dependencies (no right to stop,
voice only) and is REPEATABLE on a schedule — a notification contract,
not a one-shot shout; the repeat schedule has no default and MUST be
declared (owner: I12). Escalation without a journal entry is a
B5-failure (same class as halt-without-alert). A system aware of a
failure that does not escalate degrades silently.

**Halt / escalate boundary.** Halt applies to the own process (right to
stop = obligation to alert); escalate applies to external dependencies
(no right to stop, voice only). On conflict (both conditions met): halt
dominates (safety) + escalate the owner. A `flagged degradation` MUST be
observable in the sink — otherwise the degradation is silent = B5.

Adjacent, not covering: SPEC §2.3 (appeal-escalation + operator SLA)
shares vocabulary only (different trigger, different mechanism); closing
this gap with "already in §2.3" is rejected in advance.

Deferred (v0.4 list): per-scope/per-subject counter partitioning (cf.
E10 cap semantics); per-deployment tumbling-window adoption.

Glossary (frozen; redefinition only via separate sanction):
`policy triple` — threshold + window {type, size} + action, three
independent literals, never glued; `equality key` (signature) — the
declared field that defines "identical" events; `work_sink` — declared
store of recorded side-effects; `alert sink` — persistent store holding
the halt alert, readable after halt; `halt` — stop of the own process;
`escalate` — notification contract to external dependencies, repeatable
on a declared schedule.
---EN END---

## (б) RU-зеркало — SPEC-RU.md, раздел «### 3.4 Логирование»
(дописать в конец раздела; существующий текст не менять)

---RU BEGIN---
`threshold`, `window {type, size}`, `action` и ключи равенства классовых
счётчиков ниже — настройки расширения политики (см. `extensions.policy`
в maqs-way-standard.json); они не входят в ядро модели данных
(`schema_version way-v0.1.3`, заморожена). Журналы алертов и записи
эскалаций переиспользуют существующую инфраструктуру логирования
(hash-цепочка, retention по `logging.retention`); новых полей модели
данных не вводится.

Каждый классовый счётчик объявляет ТРИ независимых литерала (никогда не
склеенных): threshold N, window {type, size}, action. Порог и окно
настраиваются независимо. Типы окон: `sliding` (события внутри
скользящего окна) | `tumbling` (фиксированные корзины); `sliding` — тип
окна по умолчанию, `tumbling` требует явного объявления на деплоймент.
Каждый счётчик объявляет свой ключ равенства (сигнатуру): без ключа
«идентичные» не определены, счётчик недетерминирован — такой счётчик
отвергается.

**I10 — Бюджет шума ([IMP], MAQS I10).** Объявленные параметры (owner:
I10): `threshold` 3 (умолчание), `window` {sliding, 5m} (умолчания),
ключ равенства «warning text», `action` «aggregate». Одно и то же
предупреждение, повторённое N+ раз за интервал, агрегируется счётчиком —
N идентичных предупреждений становятся одной записью + счётчиком; после
порога поодиночке не выдаются; после N идентичных предупреждений —
дедуплицировать или эскалировать на другой уровень. B5-связка: заявленный успех без
выполненной работы — отказ класса B5, обнаруживается как чистая функция
от (claimed_events, performed_actions) над объявленным `work_sink`
(зафиксированные побочные эффекты; нет умолчания — ОБЯЗАН быть объявлен
при применении проверки, owner: I10); заявленный успех + пустой
приёмник → RED. I10 существует, чтобы дублирующий шум не маскировал
ложный успех.

**I11 — Цикл восстановления ([CRIT], MAQS I11).** Объявленные параметры
(owner: I11): `threshold` 3 (умолчание), `window` {sliding, 10m}
(умолчания), ключ равенства «exit code», `action` «halt+alert». Любой
автоматический рестарт (systemd/supervisor/self-heal) сопровождается
диагностическим следом первопричины. Цикл восстановления без диагноза
запрещён: после N повторов без диагноза — halt и alert, никогда не
вечный рестарт. Halt останавливает СОБСТВЕННЫЙ процесс; halt-без-alert
запрещён ровно так же, как restart-без-диагноза. Приёмник алертов —
РЕАЛЬНОЕ персистентное хранилище (журнал-файл / syslog; нет умолчания —
ОБЯЗАН быть объявлен, должен читаться после halt, owner: I11), никогда
не голые stderr/exit code: stderr не переживает halt, exit code виден
только родителю. Алерт, который нельзя прочитать после halt, —
silent-fail (класс B5). Верификация читает след ПОСЛЕ halt из приёмника.

**I12 — Бюджет эскалации ([CRIT], MAQS I12).** Объявленные параметры
(owner: I12): `threshold` 3 (умолчание), `window` {sliding, 1h}
(умолчания), ключ равенства «dependency + error code», `action`
«escalate». Повторяющийся отказ зависимости с идентичной сигнатурой
эскалируется после N вхождений (alert / halt / flagged degradation) —
никогда не опрашивает бесконечно. Escalate адресован ВНЕШНИМ
зависимостям (нет права останавливать, только голос) и ПОВТОРЯЕМ по
расписанию — контракт уведомлений, а не одиночный выкрик; расписание
повторов не имеет умолчания и ОБЯЗАНО быть объявленным (owner: I12).
Эскалация без записи в журнале — отказ класса B5 (тот же класс, что
halt-без-alert). Система, знающая об отказе и не эскалирующая,
деградирует молча.

**Граница halt / escalate.** Halt применяется к собственному процессу
(право остановить = обязанность подать alert); escalate — к внешним
зависимостям (нет права останавливать, только голос). При конфликте
(выполнены оба условия): halt доминирует (безопасность) + escalate
владельцу. `flagged degradation` ОБЯЗАН быть наблюдаемым в приёмнике —
иначе деградация молчалива = B5.

Смежное, не покрывающее: SPEC §2.3 (appeal-эскалация + SLA оператора)
делит только словарь (другой триггер, другой механизм); закрытие этого
gap'а словами «уже есть в §2.3» отвергается заранее.

Отложено (список v0.4): per-scope/per-subject разбиение счётчиков (ср.
семантика квоты E10); переход деплойментов на tumbling-окна.

Глоссарий (заморожен; переопределение — только отдельной санкцией):
`policy triple` — threshold + window {type, size} + action, три
независимых литерала, никогда не склеенных; `equality key` (сигнатура) —
объявленное поле, определяющее «идентичные» события; `work_sink` —
объявленное хранилище зафиксированных побочных эффектов; `alert sink` —
персистентное хранилище, держащее halt-алерт и читаемое после halt;
`halt` — остановка собственного процесса; `escalate` — контракт
уведомлений внешним зависимостям, повторяемый по объявленному
расписанию.
---RU END---
